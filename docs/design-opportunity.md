# پایش فرآیند فرصت طراحی

این نما یک نمونه وب تعاملی برای آماده‌سازی داشبورد Power BI است؛ فایل PBIX یا گزارش Power BI متصل نیست. ساختار فرآیند از متن ارسالی کاربر استخراج شده، نه از خواندن مستقیم CRM. تمام ۲۲ پرونده، مراکز، مسئولان، تاریخ‌ها و هدف‌های زمانی آزمایشی‌اند.

## صفحات پیشنهادی Power BI

| صفحه | محتوای اصلی | تعامل |
|---|---|---|
| نمای فرآیند | پرونده‌های فعال، انتظار، نیازمند پیگیری، موفق و ناموفق؛ تعداد یکتای فعلی هر مرحله | انتخاب مرحله، خدمت، مسئول و کارتابل؛ drill-through پرونده |
| کارتابل‌ها و گلوگاه‌ها | تعداد پرونده فعلی، میانه ماندگاری، هدف مصوب و پرونده‌های بیش از هدف | مرحله کلی و کارتابل دو فیلتر مستقل؛ نمایش پوشش تاریخچه |
| اصلاح و کیفیت | تعداد پرونده‌های دارای اصلاح و تعداد رویدادهای برگشت، تفکیک منبع و مقصد | عدم تأیید، اصلاح است؛ به شمارش شکست اضافه نمی‌شود |
| انتظار و مالی | انتظار پیش‌فاکتور و تسویه، تاریخ پیگیری، ماندگاری و تاریخ بازگشت | مسیر expire/break و تخصیص مقدار جدا از لغو |
| جزئیات پرونده | مرحله کلی، گره فعلی، مسئول فعلی و قبلی، ورود/خروج و timeline | تاریخچه کامل شامل اقدامات خودکار و بازدیدهای تکراری |

چیدمان RTL، فونت Vazirmatn، رنگ‌های آبی #005098، سرمه‌ای #082d4c و طلایی #b58c56 را با نمونه وب هماهنگ کنید. اهداف زمانی فعلی صرفاً نمونه‌اند و پیش از اتصال باید با اهداف مصوب جایگزین یا حذف شوند. صفر پرونده با «داده موجود نیست» متفاوت است.

## قواعد مدل‌سازی

- `assets/process-definition.js`: مرحله کلی (`phases`) از گره اجرایی (`stages`) جداست. نام `stages` در قرارداد کد به معنی گره‌های کارتابل، انتظار، اقدام، تصمیم، تغییر وضعیت و پایان است؛ فیلد `phaseId` مرحله کلی را مشخص می‌کند.
- تغییر مرحله در ورودی مرحله جدید منعکس می‌شود. نودهای تغییر مرحله، اگر در API دارای رویداد مستقل باشند، باید در تاریخچه اصلی حفظ شوند؛ مدل فعلی تاریخچه آزمایشی، رویداد مستقل تغییر مرحله تولید نمی‌کند.
- گره «نهایی» مشترک است؛ نتیجه از آخرین وضعیت موفق/ناموفق پیش از آن استخراج می‌شود. وقتی آن وضعیت معلوم نیست، نتیجه نامعلوم است؛ موفقیت تخمین زده نمی‌شود.
- رد مالی مرحله جاری را تا تغییر وضعیت نگه می‌دارد. گره نهایی مرحله موفق یا ناموفق قبلی را به ارث می‌برد.
- رد پرینت اصلی به **بررسی پرینت** می‌رود؛ رد تأییدیه تست یک/دو به **بررسی همان تست** می‌رود، نه مستقیم به انجام تست.
- نیاز به تست دوم، سه‌حالته است: بله، خیر، نامعلوم. فقط «بله» وارد مخرج شاخص‌های تست دوم می‌شود. «خیر» به عکاسی می‌رود و به معنای نقص مرحله نیست.
- انتظار مالی شکست نیست. هر دو خروجی `expire` و `break` به تخصیص مقدار و سپس همان کارتابل بازمی‌گردند؛ ساعت اضافه صفر است.
- شمارش فعلی هر مرحله بر اساس آخرین وضعیت پرونده است. تعداد دفعات ورود، رویداد است و ممکن است از تعداد پرونده‌ها بیشتر باشد.
- زمان حضور کارتابل از آخرین ورود به گره جاری؛ زمان حضور مرحله کلی از آغاز **حضور پیوسته فعلی** در آن مرحله. حضورهای قدیمی برای اصلاح به حضور فعلی اضافه نمی‌شوند؛ تاریخچه کامل برای جمع مدت‌های گذشته لازم است.
- اگر تنها وضعیت فعلی موجود است، زمان ورود، مسئول قبلی، شمار اصلاح و مدت انتظار نامعلوم باقی می‌مانند. پرونده‌های بدون زمان معلوم از میانگین خارج و تعداد پرونده‌های قابل محاسبه نمایش داده می‌شود.

## اتصال آینده و قرارداد داده

`workflowAdapter.load()` فعلاً فقط داده آزمایشی معتبر را می‌خواند. جایگزینی آن باید از API پشتیبان احرازشده صورت گیرد؛ این کار در مرورگر GitHub Pages، با کوکی CRM یا توکن عمومی انجام نمی‌شود. API فعلی پروژه برای خواندن داده فروش است و هنوز endpoint تاریخچه فرآیند ندارد.

پشتیبانی پیام‌گستر باید قرارداد احرازشده برای این موارد را تأیید کند:

1. تعریف نمودار `40bae1c6-7eba-4c3c-904d-243088fe6ef1` و GUID واقعی مراحل، کارتابل‌ها و خروجی‌ها.
2. وضعیت آخر هر فرصت طراحی؛ شناسه داخلی پرونده، خدمت، مرکز مجاز، مسئول و گره/مرحله جاری.
3. audit log تغییر وضعیت و تخصیص: ترتیب رویداد، زمان ورود/خروج، مسئول از/به، خروجی انتخاب‌شده و زمان قطع انتظار. صرف داده نمودار این تاریخچه را تأمین نمی‌کند.
4. مقدار دقیق `نیار به تست دوم دارد؟`، `تاریخ پیگیری پیش فاکتور` و `تاریخ پیگیری تسویه`.
5. timezone تاریخ CRM، حذف منطقی، صفحه‌بندی، سقف درخواست و مجوز دسترسی هر کاربر.

نام نمایشی با نام منبع جدا نگه داشته می‌شود: «مزحله طراحی» ← «طراحی و تأییدها»، «مرحله شتستشو» ← «شستشو و استریل». در اتصال واقعی، نگاشت **بر اساس GUID تأییدشده** است؛ تطبیق مبهم متن اجازه حذف یا ادغام وضعیت‌ها را نمی‌دهد.

هر visit شامل `id`, `stageId`, `enteredAt`, `exitedAt`, `assigneeId`, و در خروج انتظار `transitionOutcome` است. هر case شامل `historyComplete`, `needsSecondTest`, `followUpAt` و تاریخچه ترتیب‌دار است. تاریخ‌ها ISO با offset مشخص؛ محاسبات UTC و نمایش ایران/تقویم فارسی. خروجی backend باید فاقد اطلاعات بیمار و با کنترل دسترسی باشد.

## مدل ستاره‌ای Power BI

- `FactCase`: یک سطر در هر پرونده در snapshot؛ `CaseId`, `CurrentPhaseId`, `CurrentNodeId`, `CurrentOwnerId`, `PreviousOwnerId`, `ServiceId`, `CreatedAtUtc`, `CurrentEnteredAtUtc` (nullable), `Outcome`, `NeedsSecondTest` (nullable), `CompletedTest2`, `HistoryComplete`, `SampleTargetDays` (nullable), `PrepaymentWaitDays`, `SettlementWaitDays`, `ReturnCount` (این سه فقط با تاریخچه کامل).
- `FactVisit`: یک سطر در هر حضور؛ `VisitId`, `CaseId`, `NodeId`, `PhaseId`, `OwnerId`, `EnteredAtUtc`, `ExitedAtUtc`, `TransitionKind` و `TransitionOutcome`. تکرار گره مجاز است؛ VisitId یکتا.
- `DimPhase`, `DimNode`, `DimOwner`, `DimService`: مرتب‌سازی مرحله بر اساس `BusinessOrder`، برچسب نمایشی و نام/GUID منبع جدا.
- `Snapshot`: یک سطر `AsOfUtc`؛ زمان refresh مشخص و ثابت، جایگزین NOW برای گزارش قابل بازتولید.
- ابعاد به `FactCase` یک‌به‌چند و جهت فیلتر یک‌طرفه. `FactCase` به `FactVisit` یک‌به‌چند و یک‌طرفه. ابعاد مستقلی مانند `DimVisitNode` و `DimVisitOwner` برای نمودارهای تاریخی استفاده شود تا مسیر فیلتر مبهم ایجاد نشود.

فایل [measures.dax](../powerbi/measures.dax) الگوی شاخص‌هاست و باید با مدل فوق در Power BI Desktop ساخته و اعتبارسنجی شود. خود فایل DAX در Desktop اجرا یا به PBIX تبدیل نشده است. بازه تاریخ ایجاد پرونده، جمعیت cohort را فیلتر می‌کند؛ با snapshot فعلی، روند تاریخی backlog قابل استنتاج نیست. روند backlog واقعی نیازمند snapshotهای دوره‌ای است.

گزارش خصوصی نیازمند workspace و dataset واقعی، کنترل دسترسی/RLS و embedding احرازشده با backend است. اطلاعات CRM، رمز، API secret و access token در فایل عمومی قرار نمی‌گیرند. Publish to web برای داده خصوصی مجاز نیست.

## ورود نمونه به Power BI Desktop

هشت جدول CSV کاملاً فرضی در `powerbi/demo/` قرار دارد؛ با `npm run export:powerbi-demo` بازتولید می‌شوند. در Get data → Text/CSV، UTF-8 را انتخاب کنید. تاریخ‌های ISO را در Power Query به DateTimeZone تبدیل و برای DAX به DateTime در UTC نرمال کنید. مقدارهای true/false به Logical و ستون‌های مدت به Decimal Number تبدیل شوند. خانه‌های خالی، null هستند.

روابط مدل بالا را بسازید، ستون BusinessOrder را برای ترتیب DimPhase[DisplayLabel] تعیین کنید و هر measure فایل DAX را جدا اضافه کنید. جدول DimClient اختیاری و تمام مراکز آن ساختگی است. برای تاریخچه، DimVisitNode و DimVisitOwner را از ابعاد مربوطه Reference کنید. هر پرونده در FactCase دقیقاً یک سطر دارد، ولی FactVisit حضورهای تکراری را حفظ می‌کند. فایل‌های CSV داده واقعی و فایل اجرایی PBIX نیستند.
